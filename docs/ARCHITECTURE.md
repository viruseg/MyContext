# Архитектура MyContext

Материал для ИИ и для того, кто правит код. **README — про использование:** что умеет,
как подключить, какие поля и методы есть. Этот файл — про то, как устроено внутри и
почему именно так; здесь же инварианты, нарушение которых ломает библиотеку незаметно.

Правило разделения: любое утверждение о **поведении** живёт в README, любое
утверждение о **причине** поведения — здесь.

## Карта модулей

| Модуль | Ответственность |
| --- | --- |
| `src/index.js` | Единственный экспорт пакета — класс `MyContext`. Больше ничего наружу не отдаётся. |
| `src/MyContext.js` | Экземпляр целиком: состояние, показ, закрытие, разбор, привязка, жизненный цикл жеста удержания, реестр живых экземпляров, события. Самый крупный модуль. |
| `src/layer.js` | Один уровень меню как элемент Top Layer: `popover="manual"`, жизненный цикл показа и скрытия, анимация выхода, подменю, приём отдачи управления извне. |
| `src/positioner.js` | Геометрия: где поставить уровень, в какую сторону развернуть, когда развернуть влево. |
| `src/geometry.js` | Расстояние от точки до набора прямоугольников — база для `autoHideDistance`. |
| `src/renderer.js` | Сборка уровня из пунктов: проверки (`assertItem`, `assertItems`, `assertIcon`), отпечаток состава (`submenuHashOf`), отрисовка уровня и его обновление без перестроения. |
| `src/icons.js` | Разбор и санация иконок трёх типов: `svg` (недоверенная разметка, белые списки), `emoji`, `raster`. |
| `src/keyboard.js` | Клавиатурное кольцо уровня и маршрутизация клавиш между уровнями. |
| `src/scrollZones.js` | Зоны прокрутки у краёв длинного списка: геометрия, движение при удержании курсора, гашение колеса над зоной. |
| `src/hoverIntent.js` | Задержка раскрытия подменю при наведении и снятие намерения при уходе. |
| `src/theme.js` | Запись `data-vc-theme` и инлайновых CSS-переменных на уровень. |
| `src/constants.js` | Геометрические константы и значения по умолчанию. |

## Инварианты

Нарушение каждого из них даёт поломку, которую видно не сразу.

### Уровни — соседние узлы `<body>`

Каждый уровень создаётся как `popover="manual"` и подвешивается соседним узлом в
`<body>`, а **не** внутрь пункта-владельца. Причина — создание containing block:
`backdrop-filter` и анимация масштаба на родителе делают его containing block для
потомков, и позиционирование уровня относительно вьюпорта после этого ломается.

### Семь геометрических токенов обязаны совпадать с константами

| Токен | Константа |
| --- | --- |
| `--vc-padding` | `SAFETY_PADDING` |
| `--vc-item-height` | `DEFAULT_ITEM_HEIGHT` |
| `--vc-scroll-zone-height` | `SCROLL_ZONE_HEIGHT` |
| `--vc-icon-size` | `DEFAULT_ICON_SIZE` |
| `--vc-chevron-size` | `DEFAULT_CHEVRON_SIZE` |
| `--vc-radius` | `DEFAULT_RADIUS` |
| `--vc-animation-duration` | `DEFAULT_ANIMATION_DURATION` |

Меняешь токен в `styles/mycontext.css` — меняй константу в `src/constants.js`.

Расхождение ведёт себя по-разному, и это важно понимать:

- **`--vc-padding` критичен.** Движок позиционирования измеряет элемент, уже
  ограниченный этим CSS, и считает отступ до края вьюпорта равным `--vc-padding`.
  Расхождение сдвигает решение о том, в какую сторону развернуть меню у края.
- **Остальные шесть на поведение не влияют.** Их константы читают только тесты, как
  зеркала токенов.
- `--vc-scale` в этот ряд **не входит**: у него нет константы-зеркала, потому что его
  значение задаёт автор.

### Правило файла стилей: длина — это `calc(<длина> * var(--vc-scale))`

Токены выше остаются **базовыми** величинами: они не умножаются на `--vc-scale`
сами, множитель подставляется в местах использования. Именно поэтому зеркала констант
остаются проверяемыми.

Не умножаются только: отступы от вьюпорта (`--vc-padding`, предельные
`max-width`/`max-height`), тень и размытие подложки. `CURSOR_OFFSET` и
`SUBMENU_OFFSET` — зазоры позиционирования, они тоже не растут: это гарантии движка,
а не картинка.

### Префикс `vc-` занят

Идентификаторы, которые генерирует библиотека, начинаются с `vc-` (`vc-1-0`,
`vc-1-0-sub-1`), чтобы не совпасть с чужими. Авторам это объявлено в README: свои
`id` внутри иконок надо делать уникальными на всю страницу.

### Момент проверки: конструктор или показ

Правило: **проверяй там, где значение уже существует.**

| Что | Где проверяется |
| --- | --- |
| Форма `options`, пустой корневой состав, поля-флаги | конструктор |
| `labelAction`, `iconAction`, `submenuAction`, `isEnabledAction` | на показе, из `open()` |
| Поля пункта, заданные значениями: `id`, `version`, `action`, `handoffAction`, `focusAction`, `blurAction` | конструктор и показ, по форме |

Значения читающих действий до показа не существуют, поэтому проверять их в
конструкторе не на чем, а экземпляр с негодной формой появляться не должен.

Конструктор проверяет **только корневой состав**. Состав подменю проверяет
рендеререр при сборке уровня.

### Формат пути в сообщении об ошибке

`vc-3-0:2.labelAction` — `vc-<меню>:<уровень>:<индекс пункта>.<поле>`. Путь приходит
автору в сообщении `TypeError`, и по нему пункт находится в его же массиве.

## Обоснования решений

### Поля пункта — действия, а не значения

Подпись, иконка и состав подменю заданы функциями, потому что нужны на показе, а
раньше показа их не существует.

Пять действий зовутся **на каждом показе**, а не один раз при создании экземпляра:
подпись и иконка следуют за тем, что изменилось, состав подменю отвечает на новое
состояние. Заодно это снимает вопрос про предыдущий показ: без предиката подписи
отвечали бы на состояние, которое было до показа.

### Отказ читающего действия — это отказ самого `open()`

Читающие действия (`labelAction`, `iconAction`, `submenuAction`, `isEnabledAction`)
ждёт вызывающий `open()`, и он же должен узнать об отказе. Поэтому отказ летит из
промиса `open()`, и подписчик `error` его **не отменяет**: подписчик не ждал этих
данных и не вправе решать, что делать автору. Меню при этом не показывается вовсе.

### Отказ `action` и прочих — это событие `error`

Их зовут из обработчиков DOM, возвращённый промис никто не забирает. Ждать некому, и
остаётся событие `error`. **Неотменённый отказ уходит на страницу** как непойманная
ошибка, тем же путём, что синхронный бросок из обработчика: отдельное хранилище
ошибок завело бы второй, невидимый для страницы канал утечки, и `window.onerror`
перестал бы видеть поломки автора.

### Отпечаток уровня вместо сравнения ссылок

Состав уровня задаётся значениями, а не ссылками: автор вправе отдать на каждом
показе новый массив новых пунктов, и различие ссылок само по себе ни о чём не
говорит. Поэтому перед каждым показом сверяется **отпечаток** — длина, порядок,
разделители, значения `id` и `version`:

- отпечаток совпал — уровень не перестраивается, обновляются только ответы действий;
- разошёлся — уровень перестраивается целиком вместе со всем, что из него открыто, под
  тем же `id`, потому что `aria-owns` пункта-владельца уже назван.

Запись пункта в карте действий перезаписывается всё равно: при структурно том же
составе, предъявленном новыми объектами, по клику зовётся действие **нового** пункта.

Отпечаток не различает новые объекты — и это правильно, потому что подпись, иконка и
подменю у них и так перечитываются. Когда этого мало, есть `version`: он входит в
отпечаток, и его подъём заставляет уровень перестроиться при неизменившейся структуре.
Ответственность за подъём на авторе — библиотека не знает, заменено ли действие.

### Асинхронные действия собираются параллельно

Подпись, иконка, состав подменю и доступность не зависят друг от друга, поэтому
читаются одновременно, а не по очереди: последовательный показ платил бы за это
суммой задержек.

Синхронный ответ и промис равноправны. Отсюда и тип `X | Promise<X>`: функция,
возвращающая `void`, в типе `() => Promise<void>` не подошла бы.

### Порядок промисов `focusAction` и `blurAction` не гарантируется

При быстрых переходах `focusAction` одного пункта может разрешиться позже
`blurAction` того же пункта. Библиотека не ждёт и не отменяет. Если порядок важен,
его обеспечивает автор.

### Клавиша достаётся текущему уровню, а не тому, где стоит фокус

Текущий — самый глубокий из открытых, то есть открытый последним. Это различает два
иначе неразличимых состояния: подменю, открытое мышью, оставляет фокус на владельце
в родительском уровне, и без этого правила стрелка поехала бы по строке под курсором
вместо того, что пользователь видит.

- Перемещение (`ArrowDown`, `ArrowUp`, `Home`, `End`) и уход (`ArrowLeft`, `Escape`)
  достаются **текущему** уровню. В частности, `Escape` при открытом подменю закрывает
  подменю, а не всё меню.
- Раскрытие и активация (`ArrowRight`, `Enter`, `Space`) остаются на уровне, **из
  которого пришла клавиша**: они отвечают на вопрос «что выделено», а выделение
  принадлежит уровню, где стоит фокус. Поэтому `ArrowRight` на владельце открытого
  подменю входит в него, а не в пустую строку.
- `Tab` уровней не знает: он всегда закрывает всё меню.

### Раскрытие с клавиатуры ждёт данных владельца

`ArrowRight` и `Enter` на пункте-владельце без своего действия открывают подменю, чей
состав читается на показе. При асинхронном `submenuAction` перенос фокуса происходит
после ответа — иначе фокус уехал бы в уровень, которого ещё нет.

Клавиша при этом гасится **сразу**, как и прежде: браузерное поведение `ArrowRight`
(перенос каретки в поле ввода) не должно срабатывать ни при каком ответе.

### Состоянием подменю владеет выделение, а не курсор

Так же, как в системных меню. Пока активен пункт `A`, его подменю открыто; переход на
соседний пункт того же уровня закрывает его. Возврат курсора на владельца уже
открытого подменю не меняет ничего. Уход курсором в нейтральную область — зону
прокрутки, поля меню, разделитель, пустоту страницы — подменю не закрывает ничем:
отслеживать координаты не нужно, и обработчики ухода на контейнер подменю не
навешиваются.

Снимают подменю: клик вне меню, выбор действия, `Escape`, прокрутка страницы,
`resize`, уход со страницы.

### Снятие выделения при уходе курсора — работает всегда

Правило не зависит от привязки: выделение ставит движение по уровню, снятие слушает
сам уровень, а не документ. Поэтому меню, показанное вызовом из чужого обработчика,
ведёт себя так же.

Снимается **только один раз**, пока курсор снаружи: сбрасывать на каждом движении
значило бы стирать то, что поставила клавиатура. Отметки владельцев раскрытых
подменю остаются — они означают «подменю раскрыто», а не «курсор стоит здесь».

### Наведение на отключённый пункт снимает выделение

Подсветка не должна висеть на последнем доступном пункте, пока курсор стоит на серой
строке: меню в таком виде выглядит заблокированным на том, чего пользователь не
выбирал. Отметки владельцев, раскрытых уровнем выше, остаются — они показывают путь
раскрытия, а не выбор. Закрывается подменю, открытое с уровня, на котором стоит
курсор.

Разделитель сюда не относится: он высотой в пиксель, курсор пересекает его на каждом
проходе мимо, то есть выделение мигало бы постоянно.

### Удержание курсора на зоне прокрутки снимает выделение

Подсветкой горел бы тот, кого никто не выбирал. Снимается у того уровня, чья зона под
курсором; отметки владельцев раскрытых подменю над ним остаются.

Колесо над зоной не делает ничего: ни страница не прокручивается, ни меню не
закрывается. Колесо над самим списком прокручивает список, как обычно.

### Зоны у края гаснут, а не исчезают

Исчезновение сдвинуло бы список из-под курсора ровно тогда, когда зона перестала им
двигать. Поэтому зоны скрыты от чтения с экрана и не входят в кольцо клавиатурной
навигации, но при упоре только гаснут.

### Скроллом считается сдвиг, а не событие

Правило «прокрутка закрывает меню» не закрывает меню событием `scroll`, пришедшим без
сдвига страницы: позиция сверяется с той, что была на показе, и совпадение означает,
что не прокрутилось ничего. Иначе меню у нижнего края экрана убрало бы само себя.

Прокрутка элемента сверке не подлежит: своя позиция у элемента своя, и отличить чужой
пересчёт от сдвига нечем. Поэтому прокрутка панели, сделанная кодом в том же такте,
что и показ (виртуализация списка, `scrollIntoView`), закрывает меню так же, как
пользовательская.

### Внутренним для прокрутки считается любой скролл, цель которого в дереве меню

Закрытие вызывается уездом страницы из-под привязанного контейнера, а список под ним
не уезжает и его геометрию не меняет. Листание списка чужого экземпляра на той же
странице не должно сносить соседнее меню, поэтому проверяется «в дереве какого угодно
меню», а не только этого.

### Закрытие возвращает фокус привязанному контейнеру

`close()`, `Escape` и автоскрытие возвращают фокус контейнеру: оставлять его на
гаснущем уровне нельзя. Клик по странице, скролл и `resize` фокус не возвращают —
там событие само уводит фокус.

### У `autoHideDistance` нет предыстории

«Был ли курсор в меню» не спрашивается. Поэтому меню, открытое программно (`open()`
по горячей клавише) в стороне от курсора, спрячется по первому же движению мыши. Если
это не устраивает — оставьте опцию равной `0` и закрывайте сами.

Порог `0` — это «выключено», а не «закрывать в первом же пикселе за краем»: порог
меньше `SUBMENU_OFFSET` или высоты пункта закрывал бы меню на пути к подменю и при
движении между пунктами одного уровня.

Опция живёт на **своём** слушателе `pointermove`, а не на общем списке закрытия.
Порог задают чаще всего там, где привязки нет, а глобальные слушатели заводит
`attach()`. Клик по странице, скролл и `resize` автор не просил — выдать их вместе с
порогом значило бы отдать чужое решение. Общий список `dismissible` движение в нём
уже содержит, поэтому дублировать нельзя.

### Отдача управления уходит с экрана до ожидания

`handoffAction` передаёт управление **наружу**: что и где показать, решает автор, а
меню обязано только уйти с экрана. Описание жеста и отметка «уже отдано» уходят
наружу синхронно, промис ждётся после. Иначе асинхронная отдача оставила бы на экране
мёртвое меню на всё время запроса — и до того, как автор узнает, что отдача началась.

Отсюда и порядок, видный снаружи: событие `close` нашего меню приходит раньше события
`open` чужого, а возврат фокуса на якорь — раньше показа чужого. Обратный порядок был
бы верным по частям и неверным в целом.

Отменённое отдачу повторно не зовут, поэтому одно наведение с последующим нажатием
не отдаст управление дважды. Активация зовёт действие ровно один раз на показ: наведение
планирует показ, нажатие показывает немедленно, `click` приходит следом.

### `isArmableAction` двигает решение до показа

Меню показывается по нажатию, а не по `contextmenu`. Значит, к моменту показа доступна
**цель нажатия** — и только она: подписи, иконки и доступность читаются при показе, то
есть уже после. Без предиката хост, решающий по нажатию, узнаёт о цели слишком поздно,
и подписи отвечают на предыдущий показ.

Плата за асинхронный предикат при `pressAndHold: 'left'`: выделение текста
подавляется на каждом нажатии, включая те, где предикат ответит `false`.
`preventDefault()` обязан сработать до ответа — иначе протяжка курсора к пункту
начала бы выделять текст под меню, — а значит гасит событие, ещё не зная, покажется ли
меню. С `'right'` и `'any'` вопросов нет.

### `destroy()` не шлёт событий

Его зовут и не открывая меню, а закрытие по разбору от закрытия по правилу
неотличимо: подписчик получил бы `close`, которому не предшествовало `open`. Кто снимает
экран вместе с меню, зовёт `close()` сам.

У экземпляра с `destroyOnClose` порядок обратный: `close` приходит **до** разбора,
иначе подписчик не прочитал бы закрытие вовсе.

### Реестр живых — сильные ссылки, и это нормально

Экземпляр, о котором забыли `destroy()`, удерживает слушатели и узлы `<body>` и без
реестра. `destroy()` — обязательный шаг демонтажа, а не необязательная уборка. Для
экземпляра, который демонтировать некому, шаг этот делает `destroyOnClose` сам.

### Опции проверяются по форме, а не по смыслу

Каждое значение вне перечисленного отклоняется, и на это у каждой опции своя причина:

| Опция | Что молча произошло бы без проверки |
| --- | --- |
| `theme` | неизвестное значение попало бы в разметку дословно, и тёмное приложение тихо получило бы светлое меню |
| `animationDuration` | `NaN` дал бы недействительный токен, и анимация пропала бы без единой ошибки |
| `label` | пустое имя молча записало бы `aria-label=""` |
| `scale` | `0` схлопнул бы меню до негодных габаритов, `NaN` дал бы в `calc()` раскладку, которой нет; обе поломки необратимы и не сопровождаются ошибкой |
| `pressAndHold` | любое другое значение превратилось бы в «удержание не настроено», то есть в прежнее поведение: автор задал бы жест, а меню открывалось бы по правому клику |
| `isArmableAction` | нефункция превратилась бы в «спросить некого»: автор задал бы запрет, а меню открывалось бы всё равно |
| `destroyOnClose` | молча проигнорированная опция оставила бы экземпляр жить после закрытия, и подписки копились бы по разу на каждый показ |
| `armed` / `dismissible` | молчаливое «не поднято» выдало бы опцию за сработавшую |

Ушедшие из контракта поля пункта `label`, `icon`, `submenu` и `disabled` тоже
отклоняются, а не игнорируются: оставленное автором `label: 'Открыть'` молча убрало бы
подпись, а `disabled: true` сделало бы пункт активным — и ошибка каждой из них вылезла
бы там, где её не ждут.

## Сознательные платы

Их нельзя «починить», не сломав причину. Перечислены, чтобы никто не принял их за
недосмотр.

- **CSS-escape-последовательности вида `\75 rl(...)` санация не ловит.** Проверка
  presentation-атрибутов ищет `url(` как подстроку; escape-последовательность
  разбирается уже движком CSS, и до него проверка не доходит. Закрыть это можно только
  разбором CSS — то есть зависимостью или большим самописным парсером. Если иконки
  приходят из недоверенного источника, ответ уровня платформы один: CSP владельца
  страницы (`default-src 'self'` без `'unsafe-inline'`) и иконки на своём origin.
- **Призрак уходящего меню при отдаче управления.** Уровень `MyContext` гаснет в Top
  Layer, а меню соседнего пакета живёт в обычном потоке, поэтому примерно на
  `animationDuration` видно призрак. На работу не влияет: на `.vc-menu[data-vc-closing]`
  стоит `pointer-events: none`. Это плата за то, что родитель уходит после показа.
- **`filter`, `marker-*`, `pattern*`, `color-interpolation-filters` и текстовые
  атрибуты разрешены, хотя соответствующие элементы в белый список не входят.**
  Позиция защитная, на случай расширения списка элементов. Но **читать белый список
  атрибутов как обещание отрисовки нельзя**: сейчас `filter`, `marker`, `pattern`,
  `text` и `tspan` в белый список элементов не входят и вырезаются вместе с
  поддеревом, так что разрешённый `filter="url(#f)"` ссылается в ничто.
- **`id` внутри иконки сохраняется** — намеренно: без него `use` и градиенты не
  ссылались бы сами на себя. Плата в том, что после вставки `use href="#id"` ищет
  элемент во всём документе, то есть на странице-хозяине.
- **Легаси-псевдонимы SVG 1.1 в camelCase вырезаются**, хотя их современные аналоги
  разрешены. Причина: разбор регистрозависим, а список атрибутов точен — `localName`
  разобранного XML сохраняет регистр, и `strokeWidth` — уже не то же самое, что
  `stroke-width`. Симптом молчаливый: ничего не падает, иконка просто выглядит не так.
- **Наведение здесь плотнее (10 % против 6 %)** на тёмной подложке: та же доля
  невидимого текста не дала бы строке признака, а наведение — единственный его носитель.

## Тесты

```bash
npm test              # unit + chromium
npm run test:unit     # без браузера
npm run test:e2e      # unit + chromium
npm run typecheck     # tsc --noEmit по src/, Demo/, scripts/, tests/
```

Правила запуска — в `AGENTS.md`. Здесь только то, что неочевидно из кода.

**Порядок проверки типов обязателен:** сначала браузерная (`"types": []`, `src/**` и
`Demo/**`), и только потом node-программа (`"types": ["node"]`, `scripts/**` и
`tests/**`). Node-глобал в `src/**` или `Demo/**` ломает `npm run typecheck` именно
этим порядком. Изолированный `tsc -p tsconfig.node.json` его не увидит, потому что
юнит-тесты тянут `src/**` в node-типизацию.

В `playwright.config.js` Firefox всегда идёт с `--workers=1`: в параллельном режиме он
роняет программный композитор, и падал бы сам движок, а не код.

Отсутствие рантайм-зависимостей проверяется одной строкой:

```bash
node -e "const p=require('./package.json'); if (p.dependencies) { console.error('dependencies не должны существовать'); process.exit(1); } console.log('ok')"
```

`addEventListener` и `removeEventListener` перегружены по имени события, поэтому
`event.detail` приходит нужного типа и **писать приведения не нужно** — это
проверяется набором `tests/e2e/events.spec.js`, а не декларацией.
