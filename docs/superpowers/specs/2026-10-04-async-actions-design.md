## 1. Что и почему

Требуется, чтобы любое действие, которое передаёт автор, могло быть асинхронным и чтобы
библиотека это корректно разбирала: без молчаливых поломок, без потерянных отказов, без
меню, которое показалось не с теми данными.

| # | Требование | Место |
|---|---|---|
| 1 | Все восемь пользовательских точек входа принимают асинхронные функции | `src/renderer.js`, `src/MyContext.js` |
| 2 | Данные уровня собираются полностью и параллельно до отрисовки | `src/renderer.js:519` (`resolveItem`), `src/renderer.js:777` (`renderLevel`) |
| 3 | Показ, отменённый закрытием или новым показом, не появляется | `src/MyContext.js:2476` (`#closeMenu`) |
| 4 | Отказ действия не теряется и перехватывается по подписке | новое событие `error` |
| 5 | Асинхронный подписчик `open`/`close` не роняет страницу молча | `src/MyContext.js:1988` (`addEventListener`) |

### 1.1. Разрыв, который закрывает эта спека

1. **`isEnabledAction` и `isArmableAction` ломаются молча.** Оба сравнивают ответ с `true`
   строго (`src/renderer.js:409`, `src/MyContext.js:1529`). Промис `=== true` даёт `false`,
   то есть пункт молча исчезает из кольца роуминга, а меню молча не открывается. Автор не
   видит ничего.
2. **`labelAction`, `iconAction`, `submenuAction` падают с невнятным текстом.** Промис не
   строка, не описание и не массив, и сообщение говорит «вернуло не строку» — то есть
   врёт о причине.
3. **Переоткрытие из `action` не работает.** `#invokeItemAction` читает `#openSerial` до
   вызова и проверяет в `finally` (`src/MyContext.js:1021-1044`). Обе проверки
   синхронны, поэтому `await` внутри действия разрешается уже после того, как `finally`
   закрыл меню: синхронное действие, зовущее `open()`, отменяет закрытие, а асинхронное —
   нет. Наблюдаемое различие — выход, `close`, `open` и возврат фокуса на якорь и обратно.
4. **Отказ `action` и `handoffAction` уходит в `unhandledrejection`.** Возврат никто не
   держит, ловить нечем. Для синхронного броска браузер показывает непойманную ошибку, и
   это задокументировано; для отказа промиса библиотека не делает ничего.
5. **Асинхронная отдача убивает живой жест.** `#handOverTo` снимает меню с экрана до
   вызова действия (`src/MyContext.js:2848`), а `#closeMenu` при этом гасит `#armedPress`
   и снимает `pointerup`-подписку (`src/MyContext.js:2486-2490`). Если действие ждёт, то
   ребёнок вооружается уже после того, как физическое отпускание прошло и было
   проигнорировано, — вооружённое меню нечем закрыть.
6. **Предикат `isArmableAction` стоит в одном шаге от `preventDefault`.** Вся ветка
   показа по нажатию — одно синхронное решение (`src/MyContext.js:1466-1471`), и
   `preventDefault()` в ней работает только пока событие разбирается. Это единственное
   место во всей библиотеке, где «подождём» невозможно физически, и оно разобрано
   отдельно в §3.4.

## 2. Решения, принятые по ходу

Шесть мест не выводились из требований, и по ним решение принято явно.

1. **Один путь вызова, без проверки на промис.** Все действия ждётся безусловным `await`.
   Ветки вида «если вернулся промис, поступить иначе» не будет: `await` на синхронном
   значении — это один такт микроочереди, а не отдельная ветка. Причина техническая, а не
   стилистическая: `await` отдаёт управление только раньше следующей задачи, а вводные
   события — задачи. Значит между `await` и продолжением не может вклиниться ни один
   клик и ни одно отпускание, и отложенный на микротаску показ неотличим от
   синхронного — ни мигания, ни окна для повторной активации.
2. **Возвращаемое значение нужно до отрисовки, поэтому сбор идёт раньше рисования.**
   `labelAction` обязателен и задаёт высоту пункта, `submenuAction` решает, рисуется ли
   шеврон и `aria-owns`, `isEnabledAction` — кто попадёт в кольцо роуминга. Пока эти три
   не получены, уровень нечем мерить, а показывать нечего. Отсюда: `resolveItem` читает
   четыре действия параллельно, `renderLevel` делает два прохода.
3. **Замена показа отменяет его целиком.** Показ, данные которого не успели собрать к
   моменту отпускания кнопки, не показывается вовсе. Исполнить действие пункта, которого
   человек не видел, нельзя, а показать меню после отпускания — значит показать его под
   жестом, которого уже нет.
4. **Отказ читающего действия летит из промиса `open()`, а не в событие `error`.** Автор,
   ждущий `open()`, ловит его сам. Отправлять такой отказ подписчику нельзя: отменённый
   отказ оставил бы меню с неполным составом, и «обработанная» ошибка превратилась бы в
   тихо негодное меню.
5. **Подписчики получают обёртку, а не собственную рассылку.** Нативный `dispatchEvent`
   промисы не ждёт и отказов не отдаёт — библиотека их не видит и сделать с ними ничего не
   может. Своя рассылка означала бы ручную реализацию `once`, `signal`, `capture` и
   `preventDefault`; обёртка сохраняет платформу целиком и добавляет одну строку.
6. **`preventDefault()` не ждёт предиката — гасим по кнопке, откатываем по предикату.**
   `preventDefault()` работает только пока событие разбирается, поэтому асинхронный
   `isArmableAction` не может решать, гасить ли событие по умолчанию. Он решает только,
   показывать ли меню. Подробно — §3.4.

## 3. Контракт: что становится асинхронным

Все восемь точек. Типы в JSDOC разводятся явно — `T` → `T | Promise<T>`, `void` →
`void | Promise<void>`.

| Действие | Где вызывается | Новая сигнатура |
|---|---|---|
| `MenuItem.labelAction` | `src/renderer.js:421` (`labelOf`) | `() => string \| Promise<string>` |
| `MenuItem.iconAction` | `src/renderer.js:440` (`iconOf`) | `() => IconConfig \| Promise<IconConfig>` |
| `MenuItem.submenuAction` | `src/renderer.js:455` (`submenuOf`) | `() => Array<MenuItem \| SeparatorItem> \| Promise<…>` |
| `MenuItem.isEnabledAction` | `src/renderer.js:409` (`isEnabledOf`) | `() => boolean \| Promise<boolean>` |
| `MenuItem.action` | `src/MyContext.js:1030` (`#invokeItemAction`) | `(event) => void \| Promise<void>` |
| `MenuItem.handoffAction` | `src/MyContext.js:2849` (`#handOverTo`) | `(event, handoff) => void \| Promise<void>` |
| `MyContextOptions.isArmableAction` | `src/MyContext.js:1529` (`#isArmable`) | `(event) => boolean \| Promise<boolean>` |
| подписчики `open`/`close` | `src/MyContext.js:1988` (`addEventListener`) | `(event) => void \| Promise<void>` |

### 3.1. Что меняется в публичных методах

`open(params, options)`, `openSubmenu(x, y, handoff)` и `openAsSubmenu(x, y)` возвращают
`Promise<void>`. `close()`, `destroy()`, `attach()`, `detach()` и `MyContext.closeAll()`
остаются синхронными: пользовательских действий в них нет, кроме подписчиков `close`,
которых платформа не ждёт и которые библиотека перехватывает обёрткой.

`README.md:774-783` обещает «На закрытом меню показ синхронный». Обещание переписывается:
синхронные действия дают показ до следующего кадра, асинхронные — когда данные готовы.
Обещание снимается не потому, что стало неверным, а потому, что меню, у которого
`labelAction` ждёт сеть, показать раньше нечем.

### 3.2. Что меняется во внутренней цепочке

Асинхронными становятся: `#showAt`, `#ensureLevel`, `#ensureSubmenuLevel`, `#leadAhead`,
`#openSubmenu`, `#showWhatItemLeadsTo`, `#handOverTo`, `#invokeItemAction`, `#runItemAction`,
а также `resolveItem`, `renderLevel`, `renderItem`, `refreshItems` в рендерере и
`createEntry`/`reconcile`/`ensureLevel` в слое.

`#armsPress` делится надвое (§3.4): условия «пресет включён» и «кнопка совпала» читаются
синхронно и остаются в `#armsPress`, а предикат уходит в асинхронное тело `#onGlobalPointerDown`.
Одно тело на оба условия означало бы либо вечно истинный `if`, либо `preventDefault` после
`await`.

Обработчики DOM остаются обычными функциями. Браузер возвращённый промис игнорирует, а
отказ ловит библиотека — см. §6.

### 3.3. Порядок чтения состояния

`#onItemDown` (`src/MyContext.js:1266`) подменяет `#hoverEvent` до `itemPress`, потому что
`onOpen` у `hoverIntent` читает его синхронно. После перехода `#showWhatItemLeadsTo` на
асинхронное тело `#hoverOwner` и `#hoverEvent` обязаны читаться **до** первого `await`, в
том же тике: между ними указатель успевает уйти с пункта, и показ открыл бы подменю
уже не того пункта.

### 3.4. `isArmableAction` и `preventDefault`

Единственное место, где асинхронность упирается в платформу.

Сегодня ветка целиком синхронна (`src/MyContext.js:1466-1471`):

```
if (this.#armsPress(event)) {
  event.preventDefault();
  this.#armedPress = { button: event.button, pointerId: event.pointerId };
  this.open({ x: event.clientX, y: event.clientY });
  return;
}
```

`#armsPress` содержит четыре условия, и три из них — про кнопку и положение цели — могут
быть прочитаны синхронно. Четвёртое, `isArmableAction`, ждать нельзя, потому что
`preventDefault()` после `await` уже не действует: событие к тому моменту разобрано, и
браузер выполнил действие по умолчанию.

Отсюда разделение:

1. **`preventDefault()` зовётся синхронно**, как только совпали пресет `pressAndHold` и
   кнопка нажатия — то есть когда нажатие уже признано своим. Предикат в этом решении не
   участвует.
2. **`#armedPress` ставится сразу же**, синхронно, чтобы `pointerup` в промежутке ожидания
   не потерялся: подписка на `document` уже навешена и отмена сработает (§5.4).
3. **Предикат ждётся после.** Ответ не из `true` откатывает вооружение: `#armedPress`
   снимается, меню не показывается. Откат снимает **то** вооружение, которое поставил
   этот вызов, и не трогает чужое: вооружение — состояние с владельцем, а не флаг.
4. **Условия «внутри меню» и «внутри привязанного контейнера», которые раньше стояли до
   `preventDefault()`, теперь стоят после.** Нажатие внутри уже открытого меню при
   `pressAndHold: 'left'` гасится по умолчанию, хотя раньше не гасилось. Практическая
   потеря ничтожна — подписи меню уже `user-select: none`.
5. **После `await` действует охрана поколения (§5).** Отпускание кнопки в промежутке
   ожидания зовёт `#closeMenu`, поколение растёт, и предикат, ответивший уже после
   отпускания, не открывает меню, которое никто не держит.

**Названная цена.** При `pressAndHold: 'left'` и асинхронном предикате выделение текста
подавляется на каждом нажатии в привязанном контейнере, включая те, где предикат потом
скажет «нет». Расширяется ровно тот случай, ради которого предикат написан. Синхронный
предикат этой цены не имеет: ответ приходит до `preventDefault`.

**Побочная оговорка.** Без `await` условие `#armsPress(event)` истинно всегда, потому что
промис истинен. Это ломает не «при асинхронном предикате», а вообще — значит
`#onGlobalPointerDown` обязан быть асинхронным телом, а не ждать на месте.

## 4. Сбор данных перед отрисовкой

### 4.1. Пункт

`resolveItem` становится асинхронным и читает четыре действия параллельно:

```
enabled, label, icon, submenuItems  ←  Promise.all([...])
```

Порядок вызовов автору больше не обещан и не нужен: на сборку он не влияет, а набор
действий всегда один и тот же.

`assertItem` и `assertItems` остаются синхронными: они проверяют форму пункта и не зовут
ни одного пользовательского действия. Проверка формы предшествует сбору данных и от
асинхронности не зависит.

### 4.2. Уровень

`renderLevel` становится двухпроходным:

1. `Promise.all` по всем пунктам уровня — собираются все `ResolvedItem`. Разделители
   проходят мимо `resolveItem`, как и сейчас.
2. Один синхронный проход строит DOM, `aria-owns`, шевроны и карту `actions`.

Геометрия меряется после обоих проходов, то есть по готовым подписям. Это ровно то, чего
не хватало нынешнему коду: сейчас уровень строится пункт за пунктом, и каждый `await`
растягивал бы сборку на цепочку.

Вниз по графу сбор не идёт. `submenuAction` возвращает массив, а действия его пунктов
развернутся при показе подменю — иначе открытие корневого меню ждало бы весь граф.

### 4.3. Перечитывание на каждом показе

`refreshItems` (`src/renderer.js:855`) получает ту же схему: сначала собрать все ответы
параллельно, потом применить. Иначе повторный показ по-прежнему отвечал бы синхронно, и
состояние «действие сменилось между показами» работало бы только для синхронных действий.

`submenuHashOf` остаётся синхронным: он кодирует структуру уровня — длину, порядок,
разделитель это или пункт, `id` и `version`, — а не значения действий.

### 4.4. Ошибка в данных

Отказ любого читающего действия отменяет показ: уровень не строится, цепочка не
пополняется, событие `open` не рассылается. Промис из `open()` отклоняется, и на пути
`contextmenu`, где промис никто не ждёт, отказ уходит в разбор §6.

Отказ на `refreshItems` у уже показанного уровня ведёт себя иначе: меню остаётся на экране
с данными прошлого показа. Показывать нечего — уровень уже в Top Layer, и гасить его из-за
одного негодного ответа значит ломать меню целиком из-за одного пункта. Отказ при этом
не теряется: промис из `open()` отклоняется, и автор узнаёт о нём.

## 5. Отмена висящего показа

### 5.1. Чего не хватает сейчас

`#openSerial` поднимается только в `open()` (`src/MyContext.js:2055`). `#closeMenu` его не
трогает (`src/MyContext.js:2476`), а снятие висящего показа умеет только `#cancelReopen` —
то есть отложенный таймер переоткрытия. Показ, ждущий данных, отменить нечем: он
продолжится и покажет меню после того, как всё остальное уже закрыто.

### 5.2. Что добавляется

`#closeMenu` поднимает `#openSerial` наравне с `#open()`. Охрана ставится после каждого
`await` в цепочке показа:

- `#showAt`: перед `chain.push`, перед `showRoot`, перед рассылкой `open`.
- `#ensureLevel`: перед тем, как вешать обработчики уровня и регистрировать его в движке.
  Уровень, собранный после отмены, сносится через `discardLevels` — иначе остались бы
  осиротевшие узлы, записи в `#levels` и `#actions` и подписки в `#showTargets`.
- `#leadAhead`: перед подписками на пункты. Подписка на уровень, которого не будет,
  осталась бы в `#hoverTargets` навсегда.
- `#openSubmenu`: перед `#layer.show`. Собранный, но не показанный уровень подменю иначе
  остался бы в `#chain` и в реестре движка без единого способа его закрыть.
- `#showWhatItemLeadsTo`: перед показом проверяется, что уровень-владелец всё ещё в живой
  цепочке. Окно между планированием показа по наведению и показом расширяется на время
  сбора данных, и за это время цепочка могла сойтись. Проверки «владелец ещё показан»
  раньше не требовалось именно потому, что между таймером и показом не было ничего
  асинхронного.
- `#onGlobalPointerDown` (§3.4): после `await` предиката. Без этого отказ предиката
  превращался бы в «меню открылось под отпущенной кнопкой».

`#handOverTo` охраны не требует: `#handoffDone` ставится до `await`, поэтому метка
«уже отдавали» переживает ожидание и `click`, пришедший следом, вторым вызовом не
станет.

Признак отмены один: `this.#openSerial !== serial || this.#destroyed`. `destroy()` счётчик
не поднимает — он идёт мимо `#closeMenu`, и его закрывает вторая половина признака.

`destroy()` во время висящего показа отменяет его тем же признаком: уровень, собранный
после разбора, сносится через `discardLevels`, ничего не показывается, `open` не
рассылается.

### 5.3. Отмена по решению пользователя

Отпускание при `#armedPress !== null` зовёт `#closeMenu` (`src/MyContext.js:1574`), поколение
растёт, висящий показ умирает. Это и есть выбранная семантика §2.3: меню не появляется ни
на кадр.

### 5.4. Вооружение не теряется

`#armExternalPress` и `#bindHoldHandlers` ставятся **до** первого `await` — так же, как
сейчас, в начале `open()` (`src/MyContext.js:2068`). `pointerup`-подписка на `document`
навешена синхронно, поэтому физическое отпускание не потеряется: оно придёт и отменит
показ.

`#itemUnderPointer` при отпускании ищет пункт по DOM. Показ не состоялся — пункта на
экране нет, и `#itemUnderPointer` вернёт `null`. Это следствие §2.3, а не отдельное
правило: нечего выбирать, чего не видно. `README.md:28-35` («под курсором в этот момент
окажется доступный пункт — его действие исполнится») дополняется оговоркой, что обещание
действует, когда меню успело показаться.

## 6. Отказы

### 6.1. Единый разбор

Внутренний `#reportFailure(reason, source)`:

1. `dispatchEvent(new CustomEvent('error', { detail, cancelable: true }))`, где `detail` —
   `{ reason, source }` и `source` называет действие автора (путь до поля пункта или имя
   опции).
2. `defaultPrevented` — отказ обработан, дальше тишина.
3. Иначе `queueMicrotask(() => { throw reason })`. Браузер показывает непойманную ошибку
   страницы ровно так, как он показывает сегодняшний синхронный бросок из `action`, и
   Playwright ловит то и другое одним `pageerror`.

### 6.2. Что куда уходит

| Откуда | Куда |
|---|---|
| `action` | `#reportFailure` — ждать некому, вызывающий обработчик DOM |
| `handoffAction` | `#reportFailure` |
| асинхронный подписчик `open`/`close` | `#reportFailure` через обёртку §7 |
| `isArmableAction` | `#reportFailure` — путь `pointerdown` есть обработчик DOM, и ждать некому |
| `labelAction`, `iconAction`, `submenuAction`, `isEnabledAction` | промис из `open()`; автор ловит сам |
| отказ читающего действия, сорвавший показ из обработчика DOM | `#fireAndForget` → `#reportFailure` |

### 6.3. Чего в разборе нет

Отказ **читающего** действия в `#reportFailure` не идёт, и подписчик `error` не может его
отменить: отменённый отказ оставил бы меню с неполным составом, и «обработанная» ошибка
превратилась бы в тихо негодное меню. Наружу такой отказ уходит только из промиса
`open()`, и ловить его — дело автора.

### 6.4. `#fireAndForget`

Места, где промис никто не ждёт, — обработчики DOM, путь `contextmenu`, путь
`pointerdown`. Их один внутренний помощник:

```
#fireAndForget(result, source)  →  Promise.resolve(result).catch((reason) => this.#reportFailure(reason, source))
```

Наружу он не торчит, и второго пути у действий не появляется: различаются не виды
действий, а места, где промис некому.

## 7. Подписчики `open` и `close`

`addEventListener` уже перекрыт (`src/MyContext.js:1988`). Перекрытие дополняется обёрткой:

- зовёт слушателя как есть, порядок и `preventDefault` остаются нативными;
- если результат — промис, ловит отказ в `#reportFailure` с `source` вида `open:listener`;
- обёртка кладётся в `WeakMap` по исходной ссылке, чтобы `removeEventListener` снял ту
  же функцию. Без этого снятие перестало бы работать, и это молчаливая утечка подписки на
  закрытом экземпляре.

`once`, `signal`, `capture` и `preventDefault` не трогаются: они остаются нативными.

## 8. Чем это платит

1. **README:777 «показ синхронный» снимается** — `open()` возвращает промис.
2. **Выделение текста.** При `pressAndHold: 'left'` и асинхронном `isArmableAction` левая
   кнопка мыши гасится по совпадению кнопки, а не по ответу предиката, и выделение текста
   в привязанном контейнере подавляется на каждом нажатии — включая те, где предикат
   потом скажет «нет». Подробно и с границами — §3.4. При `'none'` и при синхронном
   предикате цены нет.
3. **Тесты.** Каждый тест, где `open()`/`openAt()` зовётся и DOM меряется сразу, получает
   один тик задержки и требует `await`. Ожидания `expect` внутри `page.evaluate` тоже
   расходятся: показ успевает к моменту чтения. Основной объём работы — здесь, и он не в
   логике.
4. **Контрактные тесты.** `tests/e2e/contracts.spec.js` проверяет сигнатуры и формы полей,
   поэтому ожидаемые `() => string` и `() => void` в нём обновляются на `| Promise<…>`.
5. **`#openSerial` растёт и на закрытиях.** Надо проверить, что ни один существующий тест
   не считает `#openSerial` наблюдаемым: он приватный, но отмена показа переоткрытия
   теперь срабатывает и от закрытия, а не только от нового `open()`.

## 9. Тесты

Новые проверки, все на Chromium:

| Проверка | Что фиксирует |
|---|---|
| `labelAction: async` | подпись на месте, меню показано |
| `iconAction: async` | иконка отрисована |
| `submenuAction: async` | подменю раскрывается, шеврон и `aria-owns` на месте |
| `isEnabledAction: async () => false` | `aria-disabled="true"`, пункт не в кольце роуминга |
| `isArmableAction: async` | `pressAndHold` показывает меню |
| `isArmableAction: async` → `false` | меню не показано, вооружение снято, `pointerup` не оставил висящего показа |
| `isArmableAction: async` + `pointerup` в промежутке ожидания | меню не показано под отпущенной кнопкой |
| `action: async` + `await` + `open()` | переоткрытие работает, поколение не сбито |
| `handoffAction: async` + `await` + `openSubmenu` | ребёнок вооружён на переданную кнопку |
| медленный `labelAction` + мгновенный `pointerup` при `armed` | меню не показано вовсе |
| два `open()` подряд с задержкой | показано только последнее |
| `close()` во время висящего показа | меню не появилось, `open` не рассылалось |
| отказ `action` + подписчик `error` | событие пришло с отказом в `detail` |
| отказ `action` + `error` с `preventDefault()` | тишина, `pageerror` нет |
| отказ `action` без подписчика | `pageerror` есть |
| отказ `labelAction` | промис из `open()` отклоняется |
| отказ `labelAction` через `contextmenu` | приходит в `error` |
| асинхронный подписчик `open` | отказ подписчика приходит в `error` |
| `removeEventListener` после обёртки | подписка снята, обработчик не зовётся |

Существующие 413 проверок Chromium должны остаться зелёными после добавления `await`;
переписывание их — часть работы, а не отдельная задача.

## 10. Границы

Не меняется:

- `submenuHashOf` и отпечаток состава уровня — кодируют структуру, а не значения действий.
- Внутренний ключ пункта `${menuId}:${itemIndex}` и карта `#actions`.
- `destroyOnClose` и отложенный разбор на конец выхода.
- `close()` и остальные синхронные методы.
- Нативная семантика `EventTarget` для `open`, `close`, `error` и любых других имён:
  обёртка §7 перехватывает только отказ промиса и не трогает ни порядок, ни
  `preventDefault`, ни `once`/`signal`/`capture`.
- Внешний вид, тема, `scale`, анимация и геометрия.
