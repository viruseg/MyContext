## 1. Что и почему

Требуется, чтобы автор мог узнавать о передаче фокуса пункту меню и о её отмене: курсором
или клавиатурой, на обычном пункте и на пункте-владельце подменю, причём его действие
вправе быть как синхронным, так и асинхронным. Типовой случай — пункт, который на
наведении показывает панель превью, а на уходе её прячет.

| # | Требование | Место |
|---|---|---|
| 1 | Два новых поля пункта: `focusAction`, `blurAction` | `src/renderer.js:76`, `src/renderer.js:297` |
| 2 | Оба зовутся на обычном пункте и на пункте-владельце, одинаковым кодом | `src/keyboard.js:395`, `src/keyboard.js:414` |
| 3 | Оба зовутся мышью и клавиатурой, одинаковым кодом | `src/keyboard.js:395`, `src/keyboard.js:414` |
| 4 | Действие может быть асинхронным; отказ приходит событием `error` | `src/MyContext.js:3678` (`#fireAndForget`) |
| 5 | `focusAction` и `blurAction` парны и не расходятся | `src/MyContext.js` (новое поле `#focusedItem`) |
| 6 | Отказ ничего не подавляет | §5.1 |
| 7 | Поле недоступного пункта и разделителя не зовётся никогда | §4.6 |

### 1.1. Разрыв, который закрывает эта спека

Сегодня единственный носитель состояния «пункт выбран» — атрибут `data-active`
(`src/keyboard.js:374`), и уведомить автора о его появлении и снятии нечем: карта
активов лежит в экземпляре (`src/keyboard.js:93`), движок о ней не знает и знать не
должен, а на уровне нет ни одного поля, которое сообщало бы о смене выделения. Автор,
которому нужно что-то показать по наведению, вынужден вешать собственные
`pointerenter`/`pointerleave` на те же узлы — и расходиться с библиотекой во всём, что
касается клавиатуры: `focusin`/`focusout` там не происходят на том же предмете.

Расхождение тут не косметическое, а содержательное. **`data-active` и DOM-фокус — два
разных состояния, и в одном месте они расходятся:** `ArrowLeft` из подменю возвращает
фокус на пункт-владелец, чья отметка всё это время стояла и остаётся стоять, потому что
означает путь раскрытия (`src/keyboard.js:230`). Автор, читающий «фокус» по отметке,
получил бы `focusAction` на пункт подменю и **не получил бы `blurAction`** — панель
превью утекла бы ровно там, где пользователь ушёл из подменю.

## 2. Решения, принятые по ходу

Восемь мест не выводились из требований, и по ним решение принято явно.

1. **Основа — передача фокуса, а не отметка.** Движок сообщает о каждом своём
   перемещении фокуса между пунктами, а поле `#focusedItem` хранит, кому он сообщил
   последний раз. Отметка `data-active` при этом не читается вовсе: она переживает
   скрытие подменю намеренно и в качестве триггера годится только с натяжкой.
2. **Одно поле и один идемпотентный вход.** `KeyboardHost` получает единственный
   колбэк `itemFocusChanged(next)`; `next === null` значит «фокуса на пунктах нет».
   Два колбэка (`onFocus`/`onBlur`) заставили бы вызывающий код решать, звать ли второй
   раз при `null`, — а решение это одно и оно проверяется в одной строке.
3. **Всегда `blur` прежнего, затем `focus` нового.** Обратный порядок означал бы, что
   в момент `focusAction` предыдущий пункт ещё считался бы выбранным.
4. **Отчёт идёт и на сносе уровня, хотя отметки там не снимаются.** `forgetLevels`
   (`src/keyboard.js:685`) снимает с уровня одну запись реестра, а узлы к этому моменту
   уже сняты с документа слоем. Автору всё равно, что с узлом, — ему важно, что
   фокус ушёл с пункта, который был в фокусе.
5. **Скрытие подменю без сноса само по себе события не порождает.** Отметка переживает
   скрытие, и уровень может вернуться тем же пунктом; ложный `blur` оставил бы
   автора в состоянии «не в фокусе» при пункте, который снова в фокусе. Фокус при этом
   **передаётся**, и слот это видит: `ArrowLeft` даёт `blur` пункта подменю и `focus`
   владельца.
6. **Отказ ничего не подавляет, и ждать результата библиотека не станет.** Единственная
   альтернатива — ждать `focusAction` перед показом подменю; тогда асинхронный
   пункт-владелец раскрывал бы подменю с задержкой, а отказ блокировал бы раскрытие.
7. **Асинхронные действия не упорядочиваются и не отменяются.** Переход, случившийся
   раньше, может разрешиться позже: порядок завершения не наш. Отменять author's
   промис — значило бы гасить его работу, а не свою.
8. **Новые поля в `resolveItem` не читаются.** Они не влияют ни на подпись, ни на
   доступность, ни на подменю, а лишний элемент в `Promise.all` (`src/renderer.js:581`)
   растянул бы сбор уровня ради ничего. Функция берётся из карты `#actions` на момент
   вызова.

## 3. Контракт: что становится публичным

### 3.1. Поля пункта

| Поле | Тип | Семантика |
|---|---|---|
| `MenuItem.focusAction` | `(() => void) \| (() => Promise<void>)` | пункт получил фокус |
| `MenuItem.blurAction` | `(() => void) \| (() => Promise<void>)` | пункт потерял фокус |

Объединение двух форм, а не `() => void | Promise<void>`, — по причине, уже записанной
в `src/renderer.js:109`: у `void` на выходе есть правило совместимости, у объединения
его нет, и `focusAction: () => log.push('метка')` перестал бы подходить.

### 3.2. Что меняется в публичных методах

Ничего. `open()`, `close()`, `destroy()`, `attach()`, `detach()`, `openSubmenu()`,
`openAsSubmenu()` и `MyContext.closeAll()` сохраняют сигнатуры; набор событий
экземпляра (`open`, `close`, `error`) не расширяется. Новые поля — единственное, что
появляется на поверхности.

### 3.3. Что не меняется

- `submenuHashOf` и отпечаток состава уровня: новые поля в него не входят, как не входят
  и прочие действия.
- Внутренний ключ пункта `${menuId}:${itemIndex}` и карта `#actions`.
- `RenderedItem` и `ResolvedItem`: новых полей не получают.
- Порядок чтения состояния при показе (§3.4 спеки `2026-10-04`) — новые действия в сбор
  данных уровня не входят и на асинхронность показа не влияют.
- `destroyOnClose` и отложенный разбор на конец выхода.

### 3.4. Откуда берётся функция

Из карты `#actions` по внутреннему ключу пункта, тем же путём, что `action`
(`src/MyContext.js:1062`). Запись карты обновляется на каждом показе
(`src/renderer.js:992`), поэтому подмена `focusAction` между показами видна и здесь, без
специального чтения.

## 4. Механизм: кто и что вызывает

### 4.1. Новый колбэк хоста

```
@property {(next: RenderedItem | null) => void} itemFocusChanged
```

Движок зовёт его после того, как состояние уже применено: отметка стоит, а фокус
передан. `null` — фокус отошёл на элемент уровня или ушёл с дерева меню вовсе.

Вызов с тем же `next`, что уже лежит в `#focusedItem`, обязан быть молчаливым: движок не
различает «фокус перешёл» и «фокус остался там же». И наоборот, **отсутствие вызова —
законный ответ** «фокус с пункта не уходил»: на `clearActive` это так всегда, когда
фокус стоял не на сбрасываемом уровне, и сообщать о нём нечего (§4.2).

### 4.2. Пять мест вызова

| Место | Вызов | Переход |
|---|---|---|
| `activate` (`src/keyboard.js:395`) | `host.itemFocusChanged(item)` | стрелки, `ArrowRight` в подменю, `ArrowLeft` назад на владельца |
| `activateFromPointer` (`src/keyboard.js:414`), включая ранний выход `:415` | `host.itemFocusChanged(item)` | наведение мышью, в том числе возврат к уже отмеченному владельцу |
| `clearActive` (`src/keyboard.js:441`), **только если фокус был внутри сбрасываемого уровня** | `host.itemFocusChanged(null)` | уход курсора с дерева, курсор на зоне прокрутки, невыбираемая строка |
| `reset` (`src/keyboard.js:674`) | `host.itemFocusChanged(null)` | закрытие меню, переоткрытие |
| `forgetLevels` (`src/keyboard.js:685`), **только если у снесённого уровня есть отметка** | `host.itemFocusChanged(null)` | пункт исчез с DOM вместе с фокусом |

Условие в `forgetLevels` обязательно: снос соседнего поддерева не должен снимать фокус с
владельца уровня повыше. Отметки на снесённом уровне не снимаются — узла уже нет, и
трогать нечего, — но автору сообщается.

Условие в `clearActive` обязательно по той же причине, и оно проверяется на самом узле:
`entry.element.contains(document.activeElement)`. Фокус на пункте **чужого** уровня
остаётся на месте — смена выделения у соседа его не отбирает, — и сообщать `null` значило
бы отдать чужой пункт в небыль. Ровно этот случай и есть обычный: при подменю, открытом
мышью, фокус стоит на владельце в родительском уровне, а `clearActive` зовётся для
последнего уровня цепочки.

`reset` и `forgetLevels` условия не требуют: дерево меню уходит целиком, и фокус с любого
пункта уходит по определению.

`registerLevel` (`src/keyboard.js:529`) ничего не вызывает: он зовёт `clearMarksOf`, а
протухших отметок на нём не бывает (`reset` уже снял), и вызов был бы пустым.

### 4.3. Тело на стороне экземпляра

Одно поле `#focusedItem` (`RenderedItem | null`) и одно тело:

1. `#focusedItem === next` → выход молча. Это и есть идемпотентность, и она же снимает
   вопрос «а не звать ли вторично», не задаваясь им.
2. Читается предыдущий, поле записывается следующим — до вызова любого действия, чтобы
   авторское действие, открывшее или закрывшее меню, не наблюдало полузаписанное
   состояние.
3. Предыдущий не `null` → его `blurAction`.
4. `next` не `null` → его `focusAction`.

Оба вызова идут через `#fireAndForget` (`src/MyContext.js:3678`), потому что зовутся из
обработчиков DOM, а промис ждать некому.

### 4.4. Почему не `focusin`/`focusout` и не сравнение «до/после»

- **`focusin`/`focusout` читают не то состояние.** Подсветку ведёт `data-active`, а не
  `:focus` (`src/keyboard.js:10`). `activateFromPointer` при возврате к уже отмеченному
  пункту **возвращает фокус, не меняя отметку** (`src/keyboard.js:421`), и DOM-событие
  дало бы `focusAction` без пары. Плюс события не приходят вовсе, когда активный пункт
  исчезает вместе с узлом, — то есть ровно в случае, где автору пару нужнее всего.
- **Сравнение «до/после» в MyContext** завело бы второй источник правды о том, какой
  пункт активен. Шапка `src/keyboard.js:4` запрещает это прямо: второй владелец отметки
  развёл бы состояние по двум писателям.
- **Движок, зовущий author's action сам**, потребовал бы карты активов и разбора отказов
  в модуле, который по контракту не знает ни того, ни другого
  (`src/keyboard.js:93`).

### 4.5. Что происходит с фокусом при скрытии подменю

Ничего. `#hideSubmenuFor` (`src/MyContext.js:3134`) и `#closeCurrentLevel`
(`src/MyContext.js:3227`) скрывают уровень, но оставляют его в реестре движка: его
отметка означает «курсор стоит здесь» и обязана пережить скрытие, чтобы подменю
раскрылось тем же пунктом. Отсюда следствие, которое обязано быть записано в README:
**отметка может стоять при пункте, который фокуса не имеет.** Это уже так и без новых
полей — при мышином показе подменю фокус остаётся в родительском уровне, — но новые
поля делают это наблюдаемым для автора.

### 4.6. Что не порождает событий

- **Отключённые пункты и разделители.** Отметку они не получают (`focusable === false`),
  фокус на них не встаёт, слово «пункт» в контракте означает доступный пункт.
- **Отметки владельцев раскрытых подменю при уходе курсора.** `clearActive` снимает
  отметку последнего уровня, отметки выше остаются — и **DOM-фокус на владельцах тоже
  остаётся** (это и есть правило «фокус встаёт на элемент уровня, клавиши продолжают
  работать»). Слот не меняется, событий нет. Правило общее, а не частный случай.
- **Скрытие уровня без передачи фокуса** (§2.5).

## 5. Асинхронность и отказы

### 5.1. Единый разбор

Оба действия идут через `#fireAndForget` → `#reportFailure` (`src/MyContext.js:3633`) с
`source` вида `'focusAction'` и `'blurAction'`. Отмена тем же событием `error`, что и у
`action`, и тем же правилом: неотменённый отказ уходит на страницу как непойманная
ошибка.

### 5.2. Что отказ не делает

Не отменяет выделение (отметка уже стоит), не отменяет показ подменю (он планируется по
`openDelayMs` независимо от `focusAction`), не отменяет закрытие подменю. Подавлять
нечего: решения приняты до вызова, и отказ автора не должен отматывать состояние
меню — он должен дойти до автора через `error`.

### 5.3. Порядок завершения не гарантируется

Быстрые переходы дают пересекающиеся действия: `focusAction(A)` может разрешиться после
`blurAction(A)`. Библиотека не ждёт, не отменяет и не ставит в очередь. Если автору важен
порядок, он обеспечивает его сам — своей отменой или своим счётчиком. Обещать здесь
нечего: `focusAction` не обязан завершиться раньше следующего события, потому что он не
влияет ни на что, кроме автора.

### 5.4. Парность как следствие

`#focusedItem` имеет ровно одного предшественника и ровно одного наследника, а вызовы
идемпотентны. Поэтому:

- `focusAction`, которому не последовал `blurAction`, невозможно: закрытие, разбор и снос
  уровня закрывают слот.
- `blurAction` без предшествующего `focusAction` невозможно: выход на первом шаге.
- Повторная передача фокуса тому же пункту не порождает ничего: на первом шаге выход.

## 6. Подсветка не равна фокусу

Оговорка, которая обязана стоять и в JSDoc полей, и в README.

При `ArrowRight` на пункте-владельце фокус уходит в первый доступный пункт подменю,
поэтому приходит `blurAction` владельца — а его `data-active` **остаётся**, потому что
отметка владельца означает путь раскрытия, а не выбор. `blurAction` читается как «фокус
ушёл с меня», а не «меня сняли с выделения». Симметрично: `focusAction` приходит при
получении фокуса, а не при появлении подсветки.

## 7. Пределы

- Чужой код, уведший DOM-фокус с пункта меню (свой вызов `.focus()` или выброшенный
  узел), библиотекой не замечается до её следующей передачи фокуса. Отслеживать
  `document.activeElement` нельзя: в момент teardown он уже `body`, а Top Layer
  разбирается отложенно.
- `focusAction` не влияет на показ подменю и не задерживает его.
- События экземпляра не расширяются; отказ приходит существующим `error`.
- Один пункт не может быть «и в фокусе, и вне фокуса» — состояние одно, и оно
  персистентно между показами до снятия фокуса, закрытия меню или сноса уровня.

## 8. Чем это платит

1. **`KeyboardHost` растёт на один колбэк**, а `keyboard.js` перестаёт быть модулем,
   который «владеет двумя вещами» (`src/keyboard.js:4`) в буквальном смысле: он ещё и
   сообщает о передаче фокуса. Формулировка в шапке обновляется — иначе она врёт.
2. **`README` растёт** на два поля пункта, на абзац о подсветке-не-фокусе и на правку
   формулировок про снятие выделения.
3. **Контрактные тесты** (`tests/e2e/contracts.spec.js`) проверяют формы полей, и в
   них появятся две новые ожидаемые сигнатуры.
4. **Существующие 413 проверок Chromium должны остаться зелёными**: поля опциональны, а
   слот без наполнения молчит. Ни один тест не имеет дела до пустого `#focusedItem`.

## 9. Тесты

Новые проверки, все на Chromium:

| Проверка | Что фиксирует |
|---|---|
| `focusAction` при наведении мышью | действие звано один раз, `data-active` на пункте |
| `focusAction` при `ArrowDown` | действие звано, фокус на пункте |
| переход между пунктами | `blur` предыдущего **до** `focus` следующего, в порядке |
| повторный `focus` того же пункта | ничего не звано вторично |
| `blurAction` при уходе курсора с меню | действие звано один раз, не на каждом движении |
| уход курсора с дерева при подменю, открытом мышью | `blur` **не** пришёл: фокус остался на владельце |
| `focusAction` на пункте-владельце | зван так же, как на обычном пункте |
| `ArrowRight` на владельце | `blur` владельца, `focus` первого пункта подменю, `data-active` владельца остался |
| `ArrowLeft` из подменю | `blur` пункта подменю, `focus` владельца |
| `ArrowLeft` из подменю, затем `ArrowRight` | `focus` того же пункта подменю вторично |
| наведение мышью на пункт скрытого подменю обратно | `blur`/`focus` без ложных `blur` на скрытие |
| закрытие меню `Escape` при фокусе на пункте | `blur` пришёл, до события `close` |
| закрытие меню кликом вне при фокусе на пункте | `blur` пришёл |
| выбор пункта мышью | `blur` пришёл, затем `close` |
| `Tab` | `blur` пришёл |
| `destroyOnClose` + `destroy` | `blur` пришёл до разбора |
| снос уровня при перестроении состава | `blur` пришёл |
| снос соседнего поддерева при открытом подменю | `blur` владельца **не** пришёл |
| `focusAction: async` | зван, отсрочка не мешает меню |
| отказ `focusAction` | событие `error` с `source: 'focusAction'` |
| отказ `blurAction` | событие `error` с `source: 'blurAction'` |
| отказ с `preventDefault()` | тишина, `pageerror` нет |
| отказ без подписчика | `pageerror` есть |
| действие без аргументов | `arguments.length === 0` |
| `focusAction: 'строка'` | `TypeError` с путём до поля |
| отключённый пункт с `focusAction` | не зван никогда |
| разделитель | зваков нет |
